## LinkedIn

A Rails or LMS platform rarely becomes difficult to change overnight.

The warning signs usually arrive gradually:

- reports block web requests
- background jobs fail without useful evidence
- database queries behave differently in production
- small features require weeks of investigation
- a rewrite starts to sound easier than understanding the current system

I wrote about a more practical first step: trace one painful workflow, gather evidence, and identify the smallest change that can be verified.

Modernization should reduce uncertainty—not simply replace old code with new code.

## Optional follow-up LinkedIn post

Before recommending a rewrite, I would ask:

1. What workflow is hurting users or staff now?
2. What evidence supports that diagnosis?
3. What is the smallest change worth testing?
4. How will we know it worked?

If the fourth answer is missing, the modernization plan is not ready yet.

## Optional follow-up X post

Before a rewrite, ask four questions:

1. What hurts now?
2. What evidence proves it?
3. What is the smallest useful change?
4. How will we verify it worked?

If #4 is missing, the plan is not ready.
